# 通用组织治理与承诺生命周期

本模块位于纯 C# Core。家庭、工作单位、社团及其他领域可以共用；没有对校园名称或场景的依赖。入口为 `world.Governance` 和 `world.Agreements`，业务仍使用现有 `world.Tasks`、`world.Society.Commitments`、`world.Society.Obligations` 与 `world.Economy.Ledger`。

## 组织决策产生请求

```csharp
var organization = world.Governance.CreateOrganization("shop.operations", "shop");
world.Society.Grant("shop", "manager", GovernanceService.AssignAuthority, "shop");

bool issued = world.Governance.TryRequestTask(organization.Id, "manager",
    new OrganizationTaskRequest
    {
        RequestKey = "restock.2026-09-27.001",
        AssigneeId = "clerk",
        ActionId = "trade.restock",
        TargetId = "shelf.front",
        DueTime = world.Time + 600
    }, out var task, out var reason);
```

前提是组织关联的集体已注册，经理与店员具有当前有效成员资格，经理持有 `organization.task.assign` 授权。授权的地区和对象范围必须覆盖请求。一个请求键按“组织、发起人、RequestKey”唯一；相同参数重试返回原任务，改用不同参数会拒绝，读档后继续有效。

创建后任务为 `Pending`。此调用不设置 NPC 目标、不启动行为图、不自动接受任务。领域决策可以把请求转成效用候选，再由该 NPC 调用：

```csharp
world.Governance.TryAccept(task.Id, "clerk", out reason);
// 或 world.Governance.Decline(task.Id, "clerk", "已有更重要的约定");

// 实际动作成功后，再由领域执行器提交：
world.Governance.Complete(task.Id, "clerk");
```

接受时再次核对发起人的有效授权、双方成员资格、期限及关联承诺。接受后可以拒绝继续执行；任务状态会记录拒绝，关联债务不会因此删除。`Complete` 是领域执行器的结果提交入口，调用者必须先验证业务动作成功。

截止时刻可以完成；超过截止时刻的未完成请求变为 `Missed`。组织或关联集体失效、执行者离开集体后，未完成组织任务变为 `Cancelled`。已有任务和未履行约定仍可查询。

## 可替换治理策略

`IGovernanceStrategy` 的默认实现是 `LeaderAuthorizedGovernance`，ID 为 `LeaderAuthorized`。权限检查由服务统一执行，策略可在此基础上检查预算、岗位负载或领域程序。

```csharp
world.Governance.RegisterStrategy(new MyDomainGovernance());
organization.Governance = "my.domain.strategy";
```

策略接收组织、发起者、执行者的独立副本及派生指标，并返回批准或拒绝原因。自定义策略不序列化到存档，领域模块应在新建世界和恢复世界时重新注册。缺少指定策略会拒绝新请求，不会悄悄退回默认策略。首版没有实现投票或共识程序；这些可用该接口扩展。

## 建立多方约定

约定必须包含至少两个不同的参与方及一条义务。参与方可以是 NPC 或当前有效集体。每条义务指定债务人、债权人、数量、截止时刻，以及一个动作或一种资源。

```csharp
var agreement = world.Agreements.Propose("trade.delivery",
    new[] { "clerk", "customer" },
    new[]
    {
        new AgreementObligation
        {
            DebtorId = "clerk", CreditorId = "customer",
            ActionId = "trade.deliver", Quantity = 1,
            DueTime = world.Time + 300
        }
    }, world.Time + 300);

world.Agreements.Accept(agreement.Id, "clerk", "clerk", out reason);
world.Agreements.Accept(agreement.Id, "customer", "customer", out reason);
```

`Propose` 完成全部输入检查后一次建立记录，状态为 `Proposed`。所有参与方明确同意后才进入 `Active`。NPC 只能代表自己；集体由持有 `agreement.accept` 的代理人代表，授权的对象范围可限定到该约定 ID。未获得全部同意便超时的提案变为 `Expired`，不会记为违约。任何参与方可在激活前调用 `Decline`。

## 两种履约证据

### 资源义务

先让 `Economy.Transfer` 或 `Economy.Exchange` 完成真实原子交易，再核销：

```csharp
world.Economy.Transfer("pay.001", "buyer", "seller", "money.credit", 10);
world.Agreements.ReconcileTransfer(obligationId, "pay.001", out reason);
```

核销检查账本的付款方、收款方、资源和数量。交易必须发生于所有参与方同意之后；同一逻辑 Tick 内也按持久事件序号判断先后。交易余额可分配给多条义务，但总核销量不能超过真实交易量。重试不会重复结算，部分履约及去重证据随存档保存。

### 行为义务

债权人确认实际业务结果：

```csharp
world.Agreements.ConfirmPerformance(obligationId, "customer",
    "delivery.receipt.001", 1, out reason);
```

债务人不能自证完成。债权人是集体时，需要 `agreement.confirm` 授权。`evidenceId` 是业务收据的稳定 ID，不能被其他义务重复使用；相同数量、义务与确认人的重试幂等。该接口记录债权人的明确确认，不替代领域对动画、到达、服务内容等结果的验证。

## 违约、迟到履约与终止

- 截止时刻是包含边界；`world.Time > DueTime` 且义务尚未确认完成时，才记违约。
- Core 在每轮领域系统执行完后检查期限，使同轮业务有机会先提交结果。
- 违约记录持久保存。发生违约后仍可通过真实交易或债权人确认结清债务；全部完成时状态为 `Fulfilled`，违约历史仍存在。
- 某条义务违约，不会让其他尚未到期的义务提前违约。
- `RequestTermination(commitmentId, partyId, actorId, reason, out refusal)` 需要每个参与方同意，集体代理需要 `agreement.terminate` 授权。所有同意之前，义务继续有效；共同终止后保留已履行数量，未完成部分标记取消。
- 目标切换、退会、删除 NPC 表现或解散组织不会自动删除承诺与账户。清算、继承、争议仲裁和破产程序仍由领域实现。

领域需要在产生付款的同轮调用核销；若支付事实已经存在但一直未提交核销，期限检查仍会记录“未确认履约”。后续核销不会抹掉该历史。

## 账本派生指标

`world.Governance.DeriveMetrics(organizationId, fromTime, toTime)` 每次从事实计算任务状态、约定状态、曾记录违约的约定数以及各资源的入账、出账、净流量。种子库存不算收入；交易重试不增加指标。

任务及当前约定状态按创建时间筛选，违约历史与经济流量按事实发生时间筛选。它们用于回答不同问题，不能直接当作同一个分母计算成功率。资金流的账户所有者明确为 `AccountOwnerId = organization.CollectiveId`；共享同一集体账户的多个组织会看到同一账本，汇总时须按账户去重。

## 保存、兼容与验证

`AgreementSettlement` 保存同意、激活、核销、违约及终止历史。恢复会核对历史顺序、各方同意、状态转换、义务数量和真实经济账本，拒绝缺少证据或重复核销的存档。自定义治理策略代码由领域重新注册。

原有 `Society.CreateCommitment` 仍可用于兼容现有领域；其 `ManagedLifecycle` 默认为 `false`，不会被新服务自动推进。新增业务应采用上述提案与确认 API；旧业务需要显式迁移后才能获得这些保证。
