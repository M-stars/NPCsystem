# NPC 与地区标准包

本工程的包 ID 标识可复用内容，定义 ID 标识包内概念，场景实例 ID 标识世界中的具体 NPC 或地区。复制 Prefab 后必须换实例 ID；包 ID 和定义 ID 保持稳定，同版本内容不应原地改写，语义变化应递增版本并考虑存档迁移。包可以放在项目内不同领域目录，只要每个包根遵守同一目录合同。

## NPC 包目录

```text
<NpcPackageRoot>/
  NpcPackage.asset                 必需且文件名固定
  Prefab/Character.prefab          生成器默认名；角色 Prefab 必须在 Prefab/
  Model/Character.fbx              建包工具复制角色主体 FBX 到此处
  Rig/                             骨骼/Avatar 资源；Avatar 也可为 Model/ 内 FBX 子资源
  Animations/<动作 FBX 与 Controller>
  Materials/<材质>
  Textures/<贴图与皮肤>
  Source.md、License.txt            第三方素材的来源与许可记录
```

六个子目录都必须存在；`NpcPackageAsset`、角色 Prefab、Avatar 和 Controller 的引用必须指向同包规定目录。当前布局校验要求 Avatar 资源路径位于 `Model/` 或 `Rig/`，格式为 FBX 子资源或 `.asset`；有动画绑定时 Controller 必须在 `Animations/`，映射的 Animator 状态必须有 Motion。动作 FBX 可放在本包 `Animations/`，也可引用有独立来源与许可记录的共享动画库；Kenney 样例即引用 `Art/KayKitCharacterAnimations/`。`Character.prefab` 是建包工具的默认名，手工制作的其他 `.prefab` 文件名也能通过校验，只要位于 `Prefab/`。源文件、许可、材质与贴图应随包整理；当前校验检查目录存在，不逐一检查这些文件是否齐全或授权是否有效。

`NpcPackage.asset` 明确引用角色 Prefab、Avatar、`BodyProfile`、能力、执行器、动作和动画绑定。`BodyProfile.Rig` 为 `Humanoid` 或 `Generic`，Avatar 必须有效且类型相符；能力的 `BodyConstraint` 可为 `Any` 或对应骨骼类型。Generic 动作一般要求角色和动作使用相容骨架；Humanoid 的跨角色重定向不能直接套到 Generic 上。根节点挂唯一 `SocialNpcMarker`、`NavMeshAgent` 和 `SocialNpcNavigation`；根直下名为 `Visual` 的子节点包含 Animator。Marker 引用该 Animator，Avatar 与包声明一致，Animator Root Motion 关闭，由 NavMeshAgent 负责位置。Prefab 模板 Marker 的 `NpcInstanceId` 必须是 `template.<包 ID>`，`PackageId` 必须等于包资产的 ID；实例放入场景时写入唯一 NPC ID、显示名、角色和成员资格，并保留包绑定。

### 导航组件的启动约定

标准 NPC Prefab 的 `NavMeshAgent` 默认保存为 **禁用**；`SocialNpcNavigation` 保持启用，由它在场景 `NavMeshSurface` 注册导航数据后接管 Agent 的启用、定位和后续停用。这样避免 Prefab 加载时 Agent 先于导航数据创建而反复报错。场景仍须提供已烘焙、Agent 类型匹配且包含出生位置的 NavMesh；禁用开关不会替代正确的导航资源。

导入自己的角色时，保留根节点的 Agent 和适配器，关闭 Agent 组件勾选并保存 Prefab；不要由 Animator、其他脚本或 Prefab override 在加载阶段提前启用它。Root Motion 保持关闭，业务通过 Runner/导航适配器发起移动。包校验和生成器已同步此约定，双场景启动及角色启停已通过真实 PlayMode 专项；最终 Player 结果见[验证记录](验证记录.md)。

在 Project 窗口选中 FBX 后打开 `Tools/Social Simulation/Content Catalog`，点击“从选中 FBX 创建标准 NPC 包”，再选“自动识别骨骼”“Humanoid 骨骼”或“Generic 骨骼”。工具将 FBX **复制**到 `Assets/SocialSimulation/NpcPackages/<模型名>/Model/Character.fbx`，创建六个目录和逻辑根 Prefab，并写入默认行走/奔跑能力；原 FBX 的导入设置不受该流程修改。自动模式先按源导入设置选骨骼类型，Avatar 生成失败时尝试另一种类型。工具创建 `Source.md` 作为来源记录模板；请按实际下载内容补充许可，并为需要表现的能力配置 Controller 与动画映射，完成单包校验后再注册。

能力是显式语义声明：一个动画叫 `Interact` 不会自动授予教学、交易或管理权限。多个 NPC 包可以声明完全一致的语义能力；定义不一致会报冲突。Kenney Humanoid 样例包位于 `Assets/SocialSimulation/Art/KenneyAnimatedProtagonists/`；Kenney Blocky Generic 包位于 `Assets/SocialSimulation/NpcPackages/character_a/`，使用自身 FBX 内嵌动画，两者均已注册。组合场景的两名工人使用 Generic，其余 25 人使用 Humanoid。

## 地区包目录与 Prefab 层级

```text
<RegionPackageRoot>/
  RegionPackage.asset                 必需且文件名固定
  Prefab/Region.prefab                生成器默认名；地区 Prefab 必须在 Prefab/

Region.prefab                          ← 根节点挂唯一 SocialWorldMarker
  Zones
    <zone-local-id>                     ← SocialRegionZone(LocalId, Tag, Capacity)
      InteractionPoints
        <point-local-id>                ← SocialInteractionPoint(LocalId, ActionId, Capacity)
          ApproachAnchor               ← 可选，用于到达与朝向
  Visuals                               ← 可选，外观与碰撞
  Entrances                             ← 可选，有入口声明时必需
    <entrance-local-id>                  ← SocialRegionEntrance
```

一个 `RegionPackage.asset` 对应一个地区根定义。`RegionDefinition.Zones` 声明功能分区，本地 ID 在包内唯一；`RegionDefinition.Points` 的 `ZoneLocalId` 必须指向已声明的分区，本地交互点 ID 也要在包内唯一。Prefab 根节点必须且只能挂一个 `SocialWorldMarker`，其 `RegionDefinitionId` 与包内定义一致、`PackageId` 与包资产 ID 一致；每个直属分区及交互点都要与定义的 ID、标签、动作和容量一致。地区总容量、分区容量和交互点容量分别表达不同约束，不要求相加相等。结构之外的交互点、重复 ID、缺少标记或容器会让单包校验失败。`ApproachAnchor` 可以是交互点的子节点，不参与稳定身份。

`Bounds` 是可选的地区本地坐标边界（米），中心与尺寸对应 `SocialWorldMarker.LocalBounds`；启用后入口和交互点锚点必须在边界内。`EntranceLocalIds` 对应 `Entrances/` 直属子节点的 `SocialRegionEntrance.LocalId`。包模板不保存对其他场景实例的入口引用；场景实例才填写 `TargetRegionInstanceId` 和 `TargetEntranceLocalId`。启动时检查目标存在、入口能落在 NavMesh 上、两端有完整路径，并建立有向 `PlaceState.NeighbourIds`。入口连接声明不自动创建 NavMeshLink，也不表示禁止其他可达路线；楼层跳跃、门桥等物理路径仍要提供正确 NavMeshLink。

`OpeningHours` 使用周期内的半开区间 `[StartSeconds, EndSeconds)`，空列表表示全天开放。默认周期 `OpeningPeriodSeconds=86400`，`OpeningTimeOffsetSeconds` 定义模拟起点对应的周期偏移；例如模拟从 07:45 开始，可设偏移为 27900。跨午夜营业需拆成两段，重叠、反向或非有限区间会拒绝注册。`Access` 可要求所属集体成员资格、指定集体成员资格及带组织/对象范围的角色；所有配置条件均须满足。地区实例的 `OwnerCollectiveId` 由 Marker 显式指定。

`SocialWorldRunner.CanEnterRegion` 返回允许与拒绝原因。入场请求及实际到达会重新检查手动开关、营业时段、身份条件和容量；已在地区内的 NPC 不重复占一个名额，入场请求还计入尚未完成的入场人数。这些规则控制**目标地区的逻辑准入**：不会自动生成物理门、碰撞墙或封锁经过该地区的 NavMesh 路线。需要禁止穿越时，应另外配置实际门禁、障碍物或导航区域规则。

`SetRegionOpen` 关闭地区并清理导航、临时占用、当前活动与正在进行的职责；`UnregisterRegion` 再清除实例绑定和邻接引用。地区 GameObject 被销毁时 Runner 会进行相同注销。营业结束不会删除未来尚未开始的日程。已在地区内的人不会被自动传送出去；撤离行为由领域动作决定。交互点资源的 `Active` 表示资源本身是否启用，`RegionAvailable` 表示地区当前是否允许使用，申请占用必须同时满足两者。地区关闭、重开只更新后者；手动设为 `Active=false` 或通过 `RemoveSlot` 停用的点不会因地区重新营业而恢复。

自定义领域可在世界根组件上实现 `ISocialRegionLifecycle.OnRegionUnavailable(regionId, unloaded)`，同步取消依赖该地区的运行图。家庭与工作模块按可达动作绑定的目标地区清理图，包括等待节点之后的动作；暂停时也会立即取消，不必再推进 Tick。关闭保留尚未开始的日程，卸载则取消该地区的后续职责；已经完成的工资和交易不会撤销或重复提交。

在场景中选中符合层级的地区根，使用 `Tools/Social Simulation/Create Standard Region Package From Selection` 建包。该工具读取 `Zones` 层级生成定义，默认保存到 `Assets/SocialSimulation/RegionPackages/<地区名>/`。也可先用 `Create > Social Simulation > Region Package` 创建资产，再按目录和层级规范配置。通过 `Tools/Social Simulation/Content Catalog` 检查和注册。选中地区包后用 `Tools/Social Simulation/Instantiate Selected Region Package` 放入场景，工具会生成新的 `RegionInstanceId`；点的完整身份为 `RegionInstanceId/LocalId`，因此不同地区可重用相同本地座位名。当前示例家庭与商店包分别位于 `Domains/Household/Packages/Home/` 和 `Domains/WorkAndTrade/Packages/Shop/`。

## 注册与故障定位

`Content Catalog` 扫描时先做单包字段、布局和 Prefab 结构检查；只有显示“就绪”的包才能点击“注册”。点击后工具在临时 `SocialContentCatalogAsset` 中加入候选包，运行布局与跨包 ID、依赖、执行器的联合预验证；通过后才把引用写入正式目录资产，失败会显示诊断且不提交。已注册资产可用“校验已注册内容”重新检查。`ContentRegistry.RegisterBatch` 对内存注册状态原子提交；同一版本的定义内容冲突会被拒绝，请递增包版本并设计存档迁移。

### 当前依赖与版本能力

**状态：2026-09-30 已通过 343/343 EditMode，含新增 54 项 Core 与 11 项 Authoring 回归。** 内容目录 800×650 真实窗口显示 13 个包的 ID/版本，联合校验通过并已检查[截图](Validation/ContentCatalog-Dependencies-20260930.png)。2026-10-26 已用当日源码补齐 PlayMode 15/15、Windows 构建（0 错误、1 条配置警告）与双场景 Player（运行错误 0）验收；其后的事件重评与关系衰减批次（356/356）重新覆盖了全部四阶段。详见[验证记录](验证记录.md)。

NPC、地区和领域三种包资产在 Inspector 提供相同的两个列表：

| 配置 | 数据 | 作用 |
| --- | --- | --- |
| `Dependencies` | 包 ID 字符串 | 只要求该包存在，不限制版本；保留旧声明方式 |
| `Dependency Requirements` | `PackageId` 与 `VersionRange` | 要求已注册包存在，且实际版本符合范围 |

同一依赖 ID 只能出现一次，包括跨两个列表。自依赖、循环依赖、空项、缺少依赖、非法范围与实际版本不符都会拒绝注册。先准备所需包，再进行目录联合校验；系统不会联网下载、安装、升级或自动选择依赖版本。

#### 支持的版本语法

这是有限的数字版本协议，**不是完整 SemVer**。数字版本可有 1～3 段，各段只含 ASCII 十进制数字，范围为 `0..4294967295`；比较时省略的后段补零。`1`、`1.0`、`1.0.0` 比较相等，`1.2` 精确匹配 `1.2.0`，不代表整个 `1.2.x` 系列。

| `VersionRange` 示例 | 含义 |
| --- | --- |
| `*` | 任意非空已注册版本；可匹配旧包的不透明版本文本 |
| `1` / `1.2` / `1.2.3` | 精确数字版本，按补零后的数值比较 |
| `[1.2,2)` | 包含 `1.2.0`，不包含 `2.0.0`；上界必须大于下界 |
| `[1.2,)` | 至少为 `1.2.0`，无上界 |

不支持 `^1.2`、`~1.2`、`>=1.2 <2`、`1.2.*`、预发行或 build 标签，也不支持 `[1,2]`、`(1,2)`、缺下界 `[,2)`。范围可以有首尾空白；实际数字版本字段不可带首尾空白。无效范围不会被当作 `*`。

#### 包协议与旧内容

三种资产没有范围声明时仍输出包 schema **v1**；旧包可继续使用非空的不透明版本，例如 `release-candidate`。加入任意一项 `Dependency Requirements`，包括 `*`，会自动输出包 schema **v2**，并要求**该包自己的 `Version`** 为上述数字格式。v2 包用 `*` 依赖旧 v1 包时，目标旧包仍可保留不透明版本；使用精确或区间要求时，目标版本也必须能解析为数字。

包 schema 与存档版本是不同协议。本次 Core 世界快照仍为 **v3**，Unity 运行存档仍为 **v5**。没有范围的旧 v1 清单保留既有指纹计算；新范围声明进入语义指纹。更改范围、包协议或其他清单数据后，旧存档的内容指纹可能不匹配并被拒绝。数值比较时补零不会自动改写版本字段、清单或存档；没有自动迁移。

#### 通过代码配置

三种包资产均提供 `ConfigureDependencies(packageIds, requirements)`。调用时复制列表和每项范围要求，之后修改原输入不会改动资产；调用仍需保存资产并执行校验。

```csharp
npcPackage.ConfigureDependencies(
    new[] { "content.shared.materials" },
    new[]
    {
        new PackageDependencyRequirement
        {
            PackageId = "domain.movement",
            VersionRange = "[1.2,2)"
        }
    });
```

Core 直接构建清单时，使用 `PackageManifest.SchemaVersion = 2` 并填写 `DependencyRequirements`；不要把范围写入 `Dependencies` 的包 ID 字符串。`DomainManifest.ToPackageManifest()` 同时保留两类依赖和 schema。

注册批次会先解析依赖顺序，再向临时注册表验证；失败不提交部分包或内容。相同包 ID、版本和指纹的重复注册仍为幂等操作；同 ID 内容不同会拒绝，不原地升级。

`CombinedDemoScenario` 已改为使用 Runner 的完整已校验内容目录，并对领域引用的完整清单做幂等复核，保留 NPC/地区依赖和版本要求。它不再另建只含领域 Id/Version/Kind 的简化目录；不在 Runner 目录中或与目录不一致的领域引用会拒绝。此入口与 Authoring、Core 的联合回归已包含在 343 项 EditMode 通过报告中，完整场景与 Player 验收见[验证记录](验证记录.md)。

### 场景注册与存档检查

标准场景在 `SocialWorldRunner` 同一对象上挂恰好一个 `SocialCatalogProvider` 并指定已验证目录；缺少 Provider 会拒绝启动。Runner 先构建注册表，再按 `PackageId` 核对所有 NPC/地区实例：NPC 模板和能力来自 NPC 包，地区标签与容量来自地区定义，功能区和交互点逐项与地区包对照。模板 Prefab、场景实例和目录资产中的包 ID 必须一致；复制实例时只改变实例 ID。

场景中的成员集体通过 `SocialCollectiveMarker` 显式登记 ID、显示名、`Formal` 和 `Organization`，NPC 的 `PrimaryCollectiveId` 必须属于其 `MembershipIds`；其他成员角色通过 `MembershipRoles` 指定。集体是社会结构，不依赖 GameObject 父子关系或 `campus.*`、`trade.*` 等字符串前缀。当前组合样例使用 2 个 NPC 包、8 个地区包、3 个领域包和 8 个集体定义；9 个地区实例中的两间教室复用同一地区定义。独立社区使用同样的两个 NPC 包、4 个地区包、2 个领域包，不注册校园包。

Unity 世界存档封装 v5 保存每个注册包的 ID、版本及语义清单 SHA-256，并用 `LoadedRegionIds` 记录当前已加载的地区实例集合。加载前校验包清单、场景实例绑定和地区集合；地区 ID 不得重复，集合必须与当前场景完全相同，顺序可以不同。缺少或多出地区时先恢复相符的场景加载状态再读档；这些预校验不通过时拒绝加载，原世界保持不变。该指纹覆盖 Core 清单，不是 FBX、贴图和 Controller 二进制内容哈希；修改美术资产仍须遵循包版本管理流程。

待完成导航保存绝对模拟时间截止点 `Deadline`，读档后仅使用剩余时长，不重新赠予完整超时额度。已过期或无法恢复的导航进入失败到达处理。v5 同时要求 Core v3 的知识与承诺历史，明确拒绝旧开发封装且没有自动迁移；业务动作和行为图各自的检查点版本也须兼容，详见[使用说明](使用说明.md)。
